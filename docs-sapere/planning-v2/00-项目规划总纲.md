# Sapere 致知：项目规划总纲 v2

> 版本：v2.1；日期：2026-11-18；作者：Monday。  
> 产品：装在本机的 AI 工作台，服务学习、工作与创作。  
> 当前状态：S0 技术骨架已存在，S0 退出门槛尚未全部通过；v0.2 及以后均为规划。  
> 关联：[产品范围](01-产品范围与验收.md)、[Agent 架构](02-Agent架构与技术决策.md)、[桌面架构](03-桌面架构与数据设计.md)、[工程交付](04-里程碑与工程交付.md)、[ANATOMY 吸收](08-REVIVA-ANATOMY吸收与施工顺序.md)。

## 1. 一句话定义

**Sapere 是一个本地优先、来源可核对、修改可恢复的 AI 桌面工作台：左侧管理空间、文档、笔记、智能体、技能和任务，中间完成对话与产出，右侧挂接当前任务的工具与审阅；所有正式内容落在本地，模型可接多家服务，学习、工作和创作三种用途都能独立成立。**

它不是聊天窗口加三个模板，也不是把多个 SaaS 页面塞进 Electron。产品的核心价值是：让用户围绕自己的材料持续做完一件事，并知道用了什么、改了什么、保存了什么、下次从哪里继续。

## 2. 为什么重写

v1 已经认识到 Sapere 需要项目、资料、版本、Agent 和三条业务闭环，但在以下方面不够完整：

1. 缺少成熟桌面工作台的完整信息架构：多会话、空间/文档、笔记、任务、产出、Wiki、知识库、模型、技能、工具、MCP、设置与备份之间的关系没有落成统一骨架。
2. 接口和数据规则不够“可实施”：没有把命令、事件、表和文件清单做成唯一真相来源，后续页面容易绕过服务直接写库。
3. 桌面外壳和安全要求不够细：窗口、托盘、单实例、快捷键、主题、更新、fuses、路径边界、密钥和日志需要明确为工程门槛。
4. 阶段划分把“业务切片”放得太早，容易在文档和对话核心尚不稳定时同时引入多个领域状态。
5. 对成熟产品的拆解只到竞品优点，没有把“参考程序的反面教材”转为自己的安全与发布要求。
6. 对后台服务边界、流式收尾、相对路径和提示词模板的约束不够硬，容易在实现中退化成“每个页面一套逻辑”。

`REBUILD-SPEC.md` 给出了一个已经跑过的本地 AI 工作台结构。v2 吸收它的通用骨架，但坚持 Sapere 自己的业务、品牌、技术栈和证据链。

## 3. 用户与核心任务

首批用户是项目发起人本人及少量有相似任务的中文用户。产品先验证“一个人、一个本地工作区、持续使用”的价值。

| 场景 | 用户想完成的事 | Sapere 应提供的结果 |
| --- | --- | --- |
| 学习 | 围绕资料理解、练习、复习 | 原文与引用、可追溯作答、提示记录、到期复习；不需要先写作品 |
| 工作 | 处理 CSV 或整理资料，形成可核对报告 | 输入版本、结构化分析、真实计算、可带走的报告和结果文件 |
| 创作 | 从空白或已有稿件持续写作 | 作品/章节、上下文选择、AI 提案、版本恢复、导出 |
| 日常使用 | 不打开多个工具就能继续上次的事 | 多空间、多会话、文档/笔记、任务、产出、搜索、备份和模型设置 |

三类任务共享工作区、项目（空间）、资料、文档、任务、运行、版本和记忆，但不共享未经确认的业务结论。

## 4. 产品原则

### 4.1 先完成任务，再展示平台

用户不需要先理解 LangGraph、checkpoint、MCP 或技能包。设置和诊断可以展示技术状态，但主界面先呈现“我要做什么”和“现在完成到哪一步”。

### 4.2 本地真源，外部服务可替换

- 正式文档、资料来源、作答、分析结果、作品版本和产出保存在本地工作区。
- 模型 API、OCR、语音、搜索和外部工具是可替换服务，不作为唯一数据来源。
- 没有 Key、断网或供应商失败时，阅读、编辑、固定题、已有分析重算、搜索和导出继续可用。
- 不承诺“数据永远不出本机”；每次可能外发的内容必须在操作前可见，并明确服务去向。

### 4.3 生成内容和正式内容分开

模型输出是候选、解释或建议。正式答案、计算结果、文档新版本和业务状态由对应服务提交。模型说“已经完成”不构成成功。

### 4.4 一切修改有身份

文档、来源、题目、作品、审批和运行都有稳定 ID、版本或作用域。修改绑定 `baseRevision`、来源版本或运行 ID；版本变化后旧提案和旧审批失效。

### 4.5 跨进程能力必须走登记通道

Renderer 不导入 Node、文件系统、SQL 或 provider SDK。所有请求通过 preload 暴露的窄函数进入 Main，再由 Main 分发到对应服务。新增命令、事件或表必须先登记到 [IPC 与数据契约](06-IPC与数据契约.md)。

### 4.6 长任务可观察、可取消、可恢复

流式回答、工具调用、审批、上下文压缩、文件写入和后台任务都要有状态和事件。取消不是把按钮变灰：必须停止后续步骤、阻止旧命令提交，并如实显示已经发生的费用和副作用。

### 4.7 失败优先于假成功

未保存就是未保存，来源失效就是失效，远端 401 就是 401，迁移失败就保留旧库。不能用一个绿色提示或模型摘要替代业务验收。

### 4.8 扩展不绕过权限

Skill、工具、MCP 服务器和未来插件都不能凭提示词或配置取得额外文件、网络或模型权限。扩展只能使用被授予的能力和项目范围。

### 4.9 服务边界和流式五件套

后台按 AI、数据、文件、工作区、环境、文档、媒体、知识、扩展、外观、外壳、对外 12 个服务域拆职责；每个服务由“命令注册 + 业务实现”组成，业务层不 import Electron 窗口对象。所有流式功能统一 `started → chunk/tool → done/error/cancelled`，共享 requestId 过滤、防重复结算和监听器清理。

### 4.10 数据三条铁律

- 可变业务表必须有 `createdAt / updatedAt / deletedAt`，删除进回收站。
- 数据库只保存相对工作区根的逻辑路径或对象 ID，不保存绝对路径。
- `settings` 保存可恢复配置，localStorage 只存 UI 瞬态，Key 只进 Main Vault。

## 5. 产品结构

### 5.1 平台底座

以下 12 个服务构成桌面工作台的共同底座，不等于每个版本都要一次交付：

| # | 服务 | Sapere 内容 | 首批阶段 |
| --- | --- | --- | --- |
| 1 | AI 引擎 | Chat、Agent、Run、审批、工具、取消、恢复 | S2–S3 |
| 2 | 数据 | 空间、文档、会话、任务、产出、软删与用量 | S1–S3 |
| 3 | 文件 | 读取、写入、目录、导出、路径校验 | S1–S2 |
| 4 | 工作区 | 选择、迁移、多工作区、备份和恢复 | S1 |
| 5 | 环境 | 可选 Python/venv/包管理 | S7 |
| 6 | 文档 | PDF/OCR、DOCX/PPTX 导出 | S5 |
| 7 | 媒体 | 音视频、转写、帧、翻译、生成任务 | S5/S7 |
| 8 | 知识 | Wiki、外部知识库、网页导入 | S5 |
| 9 | 扩展 | 技能包、自定义工具、MCP | S6 |
| 10 | 外观 | 主题、令牌、快捷键、主题包 | S1/S6 |
| 11 | 外壳 | 窗口、托盘、启动、更新、缓存、日志 | S1/S8 |
| 12 | 对外 | 本地网关、微信桥 | S8 可选 |

### 5.2 Sapere 业务内核

| 领域 | 核心对象 | 不可替代的服务 |
| --- | --- | --- |
| Learning | 课程/单元、题目修订、作答、提示、复习卡 | 真实学习事件与 FSRS 调度 |
| Work | CSV 源、分析方案、运行结果、报告 | 确定性计算与可复算记录 |
| Creation | 作品、章节、设定、正文修订、提案 | 版本化编辑与提案提交 |

平台能力必须服务这三类业务，而不是反过来要求用户先学会平台。

## 6. 术语与信息架构

### 6.1 空间即项目

为避免在 UI 和数据库里同时维护“项目”和“空间”两个近似概念，v2 统一为：

- 用户看到的名称是**空间**。
- 空间内部可以继续有项目或作品等业务对象。
- 数据库主表使用 `spaces`，`mode` 取 `learn`、`work`、`create` 或 `mixed`。
- 旧规划中的“项目”语义由空间承载；需要多个独立项目时，创建多个空间，而不是复制第二套资料库。

这个约定会在迁移和 UI 文案中保持一致。若未来确实需要“空间内的项目”，再增加 `projects` 作为子级，不回头改动现有对象的归属含义。

### 6.2 主要导航

```text
工作台
├─ 对话                多会话、分组、分支
├─ 空间
│  ├─ 学习空间         课程、练习、复习、资料
│  ├─ 工作空间         CSV、分析、报告、产出
│  └─ 创作空间         作品、章节、设定、提案
├─ 文档 / 笔记
├─ Wiki / 知识库
├─ 智能体 / 技能 / 工具 / MCP
├─ 任务 / 产出 / 翻译
└─ 设置与诊断
```

### 6.3 页面与业务对象的关系

- “对话”是入口，不是所有内容的容器。
- “文档”是可编辑的正式文本；对话消息、候选稿和工具日志不能冒充文档版本。
- “产出”是任务或对话生成的可带走文件；产出不会自动成为正式文档，除非用户显式导入或提交。
- “笔记”是用户自己的记录，可关联来源和空间，但不自动参与每次模型上下文。
- “Wiki”是从来源生成、审阅和维护的知识页，必须有来源和生成状态。
- “任务”是用户或 Agent 的工作项；`run` 是执行一次任务的技术记录，两者都需要但职责不同。

## 7. 总体技术架构

```text
┌───────────────────────────── Electron 应用 ─────────────────────────────┐
│ React Renderer                                                           │
│  页面 / 编辑器 / 对话 / 表格 / 审阅 / 设置                              │
│                         │ window.sapere.request/subscribe                  │
│                    sandbox preload                                      │
│                         │ 窄 IPC、来源校验、schema、长度限制               │
│ Electron Main                                                           │
│  窗口 / 托盘 / 单实例 / 快捷键 / 对话框 / 安全策略 / 进程监督           │
│  SecretVault / ModelGateway / ToolBroker / 应用升级与备份协调            │
│           │                              │                              │
│  Backend utilityProcess          Agent utilityProcess                   │
│  领域服务、唯一业务库写者        LangChain / LangGraph / 运行器          │
│  business.sqlite                  agent-checkpoints.sqlite               │
│  文件提交 / 迁移 / 索引           工具调用 / 流事件 / 审批 / 恢复         │
│           │                              │                              │
│  Job Worker（按需）              用户配置的模型服务                      │
│  PDF / CSV / 预览 / 重任务                                               │
└─────────────────────────────────────────────────────────────────────────┘
```

### 7.1 已采用的工程事实

- Electron 45.3.2，React 19.3.1，TypeScript 7.0.2，electron-vite 6.0.0。
- LangChain 1.6.6，LangGraph 1.7.4，checkpoint 1.2.2，OpenAI adapter 1.8.4。
- `node:sqlite` 业务库和独立 checkpoint 库；不再把 `better-sqlite3` 当作 v2 前置。
- Renderer `nodeIntegration: false`、`contextIsolation: true`、`sandbox: true`。
- Main 监督 Backend/Agent，子进程不继承模型密钥和无关环境变量。
- 当前开发版在默认沙箱下已有真实桌面回归；干净 Windows、有效远端模型和真人 IME 仍待验证。

### 7.2 参考规格中的适用部分

- 主进程/渲染进程/preload 分层。
- 运行事件、流式回复、审批和产物通知。
- 空间、文档、会话、Agent、技能、工具、任务、产出和设置的工作台信息架构。
- 回收站、备份、迁移、日志、用量和更新等桌面软件基础设施。
- 安全边界、路径检查、密钥不回传、流式监听清理和长任务状态。
- 12 个后台服务、流式五件套、模型解析器、提示词模板、相对路径和组件四件套。

### 7.3 明确不适用的部分

- 不复制参考程序的品牌、图标、页面风格或技能内容。
- 不把参考程序 424 条通道、86 条路由和 480 个模块当作目标数量。
- 不采用 Vue、`better-sqlite3` 或直接向 Renderer 暴露数据库 CRUD 的做法。
- 不把本地网关、微信桥和实时语音放入 v0.2 的必经路径。
- 不承诺原程序的全部媒体、Office、OCR、微信和 Python 能力在同一版本完成。

## 8. 版本路线

### R0：S0 技术验证（当前）

目标是兑现已有骨架的工程事实：进程、SQLite、LangGraph 磁盘恢复、中文编辑、模型协议和最小安装包。退出以 S0-01–S0-07 全部通过或有经验证的替代方案，并完成 S0.5 工作台约定对齐和安全收口为准。

当前剩余阻断：有效真实远端模型、真人中文 IME、干净 Windows 安装/卸载，以及默认启动/安全加固的发布证据。

### R0.5：S0.5 工作台约定对齐

在进入完整工作台业务前，先完成命令清单、请求信封、流式五件套、审计字段/相对路径、视觉令牌、组件基座、模型解析器和提示词模板的第一批落地。详细任务见 [04 的 S0.5](04-里程碑与工程交付.md) 和 [08](08-REVIVA-ANATOMY吸收与施工顺序.md)。

### R1：v0.2 工作台闭环

第一次让用户能“持续用起来”：

- 多空间、多文档、文档修订、标签页和搜索。
- 多会话、会话分组、流式回答、取消和导出。
- Backend/Agent 的真实运行记录、工具调用、审批和恢复。
- 学习、CSV 工作、文本创作三条独立流程。
- 任务、产出、回收站、模型设置、主题、日志、退出保护和基础备份。
- 默认沙箱、路径边界、密钥保护和核心 E2E。

### R2：v0.3 知识与文档

- Wiki 页面、来源、生成、lint、语义审计和 OCR 任务。
- 外部知识库源接入、检索和请求-响应分析。
- PDF 预处理/OCR/图像导出、DOCX/PPT 导出。
- 笔记文件夹、更多搜索和上下文包。
- 媒体注册/转录/摘要和翻译。

### R3：v0.4 扩展与媒体

- 技能包安装、导入、编辑、卸载。
- 自定义工具、MCP stdio/SSE/HTTP 适配。
- 主题包和自定义 CSS 的暂存/提交/丢弃。
- 生成任务、实时 ASR、可选的本地网关。
- 可选 Python 环境，服务于明确的专业工具，而不是所有用户的启动前置。

### R4：v1.0 稳定发布

- 干净 Windows 安装/升级/卸载/回退、签名策略、更新渠道。
- 备份恢复演练、损坏数据恢复、性能和可访问性基线。
- 真实试用、问题修订和可演示的项目证据。
- 微信桥等会打开本机端口或连接外部账号的能力，默认关闭并单独解释风险。

## 9. 范围与非目标

### 9.1 v0.2 必须做

- 本地工作区、空间、文档、笔记、对话、任务、产出和回收站的基础对象。
- 三个业务空间各自能完成一条端到端流程。
- 模型配置、模型调用、流式事件、取消和错误状态。
- Agent 工具循环、审批、运行记录、checkpoint 和跨重启恢复。
- 文档版本、来源/引用、导出、备份、日志和错误诊断。
- 默认安全配置：无 Node 泄漏、无任意路径、无密钥回显、无任意 shell。

### 9.2 v0.2 不做

- 云同步、多人协作、账号体系、团队权限和跨端漫游。
- 自建模型推理服务或把某个供应商固定为首选。
- 让模型生成并直接执行任意 Python、Node、shell 或外部命令。
- 完整复刻参考程序的 90 个技能包、微信桥、媒体分析全家桶和 Office 预览。
- 永久排除上述方向；它们只是不能成为 v0.2 的隐性承诺。

### 9.3 长期保留

专业 Office、扫描件 OCR、图像/音视频生成、可视化工作流、多 Agent 团队、插件市场、知识图谱、Computer Use、移动端和团队协作继续保留为候选能力。进入版本前必须补范围、权限、成本、恢复和验收，不以“以后会有”代替规格。

## 10. 质量与证据

以下结果不能单独证明完成：

- 页面能打开。
- 模型返回了一段文字。
- 测试使用了 mock。
- 工具返回 `ok:true`。
- 架构图画得完整。

完成需要同版本的应用、锁文件、实际桌面、规定输入、预期结果、实际结果和证据路径。涉及恢复、备份、审批、模型和 IME 的任务必须在真实进程中验证；mock 只能做稳定回归。

## 11. 研发与求职表达

项目同时服务真实使用和求职展示。每个阶段保留：

- 需求/范围、ADR、数据模型和接口登记。
- 关键代码、评审、失败复盘和测量结果。
- 真实桌面、打包态和安装态证据。
- AI 辅助开发的使用范围，以及本人完成的设计、编码、调试、验证和取舍。

简历只能写已经实现并验证的功能、本人实际贡献和可重复测量结果；不把规划、依赖、截图或未来能力写成已完成成果。

## 12. 变更规则
